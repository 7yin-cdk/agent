# 数据库运维 Agent 长期记忆模块设计方案

## 一、背景与目标

当前 Agent 已有两层记忆，但都不跨会话：

- **短期记忆**（`agent_short_term_memory`）：单会话内消息，按会话隔离。
- **会话摘要**（`agent_conversation_summary`）：单会话跨轮次压缩。

缺少一层**跨会话、按用户维度持久化**的记忆。导致：同一用户每次对话都像"第一次"，无法记住用户画像（是谁、负责什么系统）、稳定偏好/约束（回答风格、哪些操作被禁止）、已解决的故障经验（下次同类问题可复用），也无法实现个性化。

本方案：新增**第三层长期记忆**，与现有两层并行，回答前召回注入、对话后异步抽取，配 CRUD 管理接口与混合保存策略。

## 二、六问总览

| # | 问题 | 结论 |
|---|---|---|
| 1 | 存什么 | 四类：**用户画像 / 偏好约束 / 实体知识 / 经验案例** |
| 2 | 怎么决定存 | **对话结束后异步 LLM 抽取**（结构化 JSON 候选）+ 用户显式"记住…"命令同步写 |
| 3 | 以什么形式存 | **单表结构化列 + content 文本 + embedding 向量(1536) + metadata JSONB**（非纯 JSON 文件，非纯向量库） |
| 4 | 怎么召回 | **混合召回**：画像/偏好"始终注入" + 实体等值过滤 + 经验向量召回 → RRF 融合 → rerank |
| 5 | 存取时机 | **存：对话后**（异步，不阻塞）；**取：对话前**（构造 prompt 时注入） |
| 6 | 永久还是淘汰 | **混合**：画像/偏好永久（LLM 合并去重防矛盾）；经验/实体按容量上限 + 重要度×最近访问衰减淘汰，支持显式过期与手动删除 |

## 三、详细设计

### 3.1 存什么内容（记忆分类）

| 类别 | 内容 | 示例 | 生命周期 |
|---|---|---|---|
| USER_PROFILE 用户画像 | 角色、职责、负责的集群/系统、技术栈 | "负责生产环境 orders 库与 prod_cluster 的运维" | 永久，LLM合并 |
| PREFERENCE 偏好 | 回答方式/格式/详略/语言 | "偏好中文、简洁、给结论先行" | 永久，LLM合并 |
| CONSTRAINT 约束 | 明确限制 | "生产库禁止 DDL""仅 >500ms 慢查询才提醒" | 永久，LLM合并 |
| ENTITY 实体知识 | 某运维对象的稳定事实（集群/库/表/任务/实例） | "prod_cluster 为 3 节点 PG14，流复制" | 容量淘汰 |
| EXPERIENCE 经验案例 | 问题→方案→结果（success/failure） | "orders 表锁等待：停 autovacuum 长事务后恢复" | 容量淘汰 |

> 判断标准：**稳定、跨会话有价值**。寒暄、纯临时指令、闲聊不存。经验案例必须记录"结果"（成功/失败），否则不构成可复用经验。
> 四类边界：**ENTITY** 讲"对象本身的事实"（集群拓扑/表结构/任务周期）；**EXPERIENCE** 讲"一次事件的处理"（问题→方案→结果）；**USER_PROFILE** 讲"用户这个人"（角色/职责/负责系统）；**CONSTRAINT** 讲"对操作的规则"（禁止/限制）。

### 3.2 怎么决定存（抽取机制）

**双通道**：

- **自动通道（主）**：每轮对话结束后，异步（`@Async`）把本轮 user / assistant / tool 消息交给 LLM，用抽取 prompt 输出**候选记忆 JSON 数组**，每条含 `category/content/keywords/entity/importance/confidence/dedup_key`。服务端解析后做去重、冲突消解、淘汰，再入库。
- **显式通道**：用户说"记住/记一下：…"（正则 `(?i)^(请)?记住|记一下|请记下`）→ 同步走抽取入库，立即生效。

选择异步的原因：① 抽取需要"整轮完整结果"，只能事后；② 不阻塞用户等待回答；③ 与现有 `ConversationSummaryServiceImpl` 轮后 `@Async` 增量摘要模式完全一致，复用同一线程池。

抽取 LLM 输出要求：只输出 JSON 数组，空则 `[]`，禁止 Markdown 代码块。（完整 prompt 模板见 §5.1）

### 3.3 以什么形式存（存储形式）

**单表 `agent_long_term_memory`（PostgreSQL），三态并存**：

- **结构化列**：user_id、category、entity、entity_type、importance、confidence、dedup_key、access_count、last_accessed_at、expired_at、is_deleted 等 —— 支撑等值过滤、分页、淘汰排序、去重。
- **content TEXT**：自包含、无指代的中文记忆正文（召回后直接进 prompt）。
- **embedding VECTOR(1536)**：复用现有 pgvector（`FloatArrayTypeHandler`）+ 百炼 text-embedding-v4 —— 支撑语义向量召回。
- **keywords TEXT[]**（GIN 索引）+ **metadata JSONB**：关键词召回与扩展元数据（如 EXPERIENCE 的 result 标记）。

> 复用现有设施：pgvector HNSW 索引、`LlmServiceImpl.embed()`、MyBatis + JSONB TypeHandler、雪花 ID。不为记忆引入独立向量库。

### 3.4 怎么召回（召回方式）

回答前，`recall(context)` 四路并行取，再融合：

1. **always-on（画像/偏好/约束）**：按 `importance DESC` 取前 5 条，每轮**无条件注入**（限量，数量少）。
2. **实体等值过滤**：从 query 正则抽取运维对象 token（如 `orders库`、`prod_cluster`、`(db|cluster|table).\w+`），`entity IN (...)` 或 `keywords && ARRAY[...]` 过滤，取 8 条。
3. **向量召回（经验案例）**：`embed(rewrittenQuery)` → `ORDER BY embedding <=> ? LIMIT 20`（`user_id + category=EXPERIENCE` 前置过滤，命中多列 HNSW 索引）。
4. **融合**：路 2、3 结果走 **RRF 融合**（复用 `RagServiceImpl.mergeByRrf`）→ `llmService.rerank` 精排取 3 条。

最终：always-on(≤5) + reranked(≤3)，截断到注入上限 6 条，写入 `AgentChatContext.longTermMemories`。被选中的记忆 `access_count+1`、`last_accessed_at=now`（供淘汰用）。

**注入格式**（`PromptBuilder` 新增 `appendLongTermMemory`，风格对齐现有 `### 参考资料`）：

```
### 长期记忆
【记忆1】[用户画像] 你是负责生产环境的数据库运维工程师，主要维护 orders 库与 prod_cluster。
【记忆2】[约束] 禁止在 prod_cluster 上执行任何 DDL 变更。
【记忆3】[经验·成功] orders 表偶发锁等待：此前通过停掉 autovacuum 相关长事务后恢复正常。
```

列表为空时整段省略（避免干扰 SIMPLE_CHAT）。`recall` 与注入整体 **fail-open**（记忆故障不得影响主流程）。

### 3.5 存取时机

| 时机 | 动作 | 位置 |
|---|---|---|
| **对话前**（回答前） | `longTermMemoryService.recall(context)` | 三个入口的 `buildChatContext` 之后、`route/routeStream` 之前 |
| **对话后**（保存消息后） | `longTermMemoryService.postTurn(...)`：判显式"记住"→ 同步写；否则转发 `@Async extractFromTurn` | 保存短期记忆之后、触发会话摘要之前 |
| 任何时刻 | 管理接口 CRUD（用户手动查看/添加/删除） | REST API |

三个聊天入口必须**对称接入**：`AgentServiceImpl.chat()`、`AgentServiceImpl.doChatStream()`、`ReactiveStreamingService.doChatAndStream()`。

### 3.6 永久还是淘汰（保存策略）

**混合策略**：

- **永久类**：USER_PROFILE / PREFERENCE / CONSTRAINT。不做 TTL；矛盾靠 **LLM 冲突消解**（合并/替换/保留/删除，见 §5.2），防无限增长设各 50 条软上限。
- **淘汰类**：ENTITY / EXPERIENCE。每用户各 200 条上限，超限即淘汰。
- **淘汰打分**：`importance ASC → last_accessed_at ASC NULLS FIRST → access_count ASC`（三级排序，SQL 可直接表达，等价于"低重要度、久未访问、低频"优先淘汰），由 `idx_ltm_evict` 部分索引覆盖。
- **触发双轨**：写入时 `evictIfNeeded`（计数超限即删）+ 每日 `@Scheduled` 清扫（物理清理过期且已逻辑删除的行）。
- **显式过期**：`expired_at` 支持（如临时维护窗口、用户"不再记住"置过期）。
- **手动删除**：管理接口逻辑删除，物理由定时清扫兜底。

### 4.3 表结构 DDL

```sql
CREATE TABLE agent_long_term_memory (
  id BIGSERIAL PRIMARY KEY,
  user_id VARCHAR(64) NOT NULL,
  category VARCHAR(32) NOT NULL,          -- USER_PROFILE/PREFERENCE/CONSTRAINT/ENTITY/EXPERIENCE
  content TEXT NOT NULL,
  keywords TEXT[] NOT NULL DEFAULT '{}',
  entity VARCHAR(255), entity_type VARCHAR(64),
  embedding VECTOR(1536),
  importance SMALLINT NOT NULL DEFAULT 5 CHECK (importance BETWEEN 1 AND 10),
  confidence DOUBLE PRECISION DEFAULT 0.8,
  dedup_key VARCHAR(128),
  access_count INTEGER DEFAULT 0, last_accessed_at TIMESTAMPTZ,
  source_conversation_id VARCHAR(64), source_turn VARCHAR(128),
  metadata JSONB NOT NULL DEFAULT '{}'::jsonb,
  is_deleted BOOLEAN NOT NULL DEFAULT FALSE,
  expired_at TIMESTAMPTZ, created_at/updated_at TIMESTAMPTZ DEFAULT now()
);
-- 去重（部分唯一索引）：uk_ltm_dedup (user_id, dedup_key) WHERE dedup_key IS NOT NULL AND is_deleted=FALSE
-- 常规：idx_ltm_user_category (user_id, category, importance DESC)；idx_ltm_entity (user_id, entity)
-- 关键词：idx_ltm_keywords USING GIN (keywords)
-- 淘汰：idx_ltm_evict (user_id, category, importance ASC, last_accessed_at ASC NULLS FIRST, access_count ASC) WHERE is_deleted=FALSE
-- 向量：HNSW (user_id, embedding vector_cosine_ops)（pgvector≥0.5 多列；低版本退化为单列）
```

## 五、关键模板

### 5.1 抽取 prompt（走 `llmService.chat()`）

```
你是数据库运维 Agent 的长期记忆抽取器。从下面这轮"用户-助手"对话（含工具结果）抽取值得长期保存的记忆，输出 JSON 数组。
只抽取五类：USER_PROFILE/PREFERENCE/CONSTRAINT/ENTITY/EXPERIENCE，命中哪类归哪类。
不抽取：寒暄、重复内容、纯临时指令、与运维无关的闲聊。
每条字段：{category, content(自包含无指代,中文), keywords[], entity, entity_type, importance(1-10), confidence(0-1), dedup_key(<CATEGORY>:<归一化主题>), result(仅EXPERIENCE)}
要求：只输出 JSON 数组；不输出 Markdown 代码块；无内容则输出 []。
### 本轮对话
user: {userQuery}  assistant: {assistantAnswer}  [tool 摘要: {toolResults}]
### 输出
[]
```

### 5.2 冲突消解 prompt（`dedup_key` 相同触发）

```
两条记忆指向同一 dedup_key，请判断处理。
旧: {oldContent} ({oldCategory}, importance={oldImportance})
新: {newContent} ({newCategory}, importance={newImportance})
- 互补/一致 → MERGE（合并成更完整表述）
- 新明确覆盖旧（数值/状态变化）→ REPLACE（以新为准）
- 新价值更低/无关 → KEEP（保留旧）
- 矛盾且无法判断 → REPLACE
只输出一行 JSON：{"action":"MERGE|REPLACE|KEEP|DELETE","content":"...","importance":n,"confidence":n}
```

EXPERIENCE 特例：同问题不同结果**保留两行**（dedup_key 加 `#<n>` 后缀），避免吞掉真实经验；结果一致才 MERGE 补充方案细节。

### 5.3 关键 SQL

```xml
<!-- 向量召回 -->
SELECT ... , 1 - (embedding <=> #{e, typeHandler=FloatArrayTypeHandler}) AS similarity
FROM agent_long_term_memory
WHERE user_id=#{userId} AND is_deleted=FALSE
  AND (expired_at IS NULL OR expired_at > CURRENT_TIMESTAMP) AND category IN ('EXPERIENCE')
ORDER BY embedding <=> #{e, typeHandler=FloatArrayTypeHandler} LIMIT #{topK}

<!-- 实体等值 + 关键词重叠（&amp;&amp; 是 XML 转义） -->
WHERE ... AND (entity IN (...) OR keywords &amp;&amp; ARRAY[...]) ORDER BY importance DESC LIMIT #{limit}

<!-- 淘汰候选 -->
WHERE user_id=#{userId} AND category=#{category} AND is_deleted=FALSE
ORDER BY importance ASC, last_accessed_at ASC NULLS FIRST, access_count ASC LIMIT #{excess}
```

## 六、实现风险与注意点

1. **三个聊天入口必须对称接入**，漏掉 `ReactiveStreamingService` 会导致 reactive 流式链路行为不一致。
2. **embedding 失败必须降级**（`embedding=NULL` 存，仍可 always-on/等值召回），不得中断主流程；抽取/召回/rerank 一律 fail-open（异常 catch + log.warn，照抄 `ConversationSummaryServiceImpl` 的 @Async 异常处理）。
3. `FloatArrayTypeHandler` 硬编码 1536 维，与 text-embedding-v4 一致。
4. MyBatis XML 中 `&&` 需转义为 `&amp;&amp;`。
5. 多列 HNSW 依赖 pgvector ≥ 0.5；低版本退化单列（每用户数据量小，可接受）。
6. `@Async`/`@Scheduled` 已启用（`AgentApplication`），复用现有异步线程池，无需新增配置。

## 七、验证方式（后续实现时）

1. **建表**：执行 `agent_long_term_memory.sql`，`EXPLAIN` 确认向量召回命中 HNSW 索引。
2. **抽取**：发起一轮包含"记住：我是负责 orders 库的运维"的对话，查库确认生成 USER_PROFILE 记忆、embedding 非空。
3. **召回**：发起相关新问题，在返回 prompt（日志或 `/agent/memories/search`）确认 `### 长期记忆` 分段被注入且内容相关。
4. **去重**：重复相同"记住"内容，确认走 MERGE 而非新增重复行。
5. **淘汰**：灌入超过容量的 EXPERIENCE 记忆，确认最不重要/最久未访问的被淘汰。
6. **CRUD**：走全量管理接口增删改查，确认 404/400 语义与 userId 隔离。
7. **回归**：`/agent/chat`、`/agent/chat/stream`、`/agent/chat/reactive/stream` 三条链路均正常，无记忆时 prompt 无 `### 长期记忆` 段。
